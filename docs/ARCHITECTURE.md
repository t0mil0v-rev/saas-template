# Архитектура

## Контекст

Система обслуживает браузерный клиент, публичные страницы организаций и
административный контур платформы. Единицей изоляции является организация.
Пользователь получает доступ к ней только через явную запись `org_members`.
Суперпользователь видит платформенную статистику и аудит, но не получает
неявную роль владельца tenant.

```text
Browser
  |
  | HTTPS, session cookie, CSRF header
  v
Caddy ---- static React bundle
  |
  | /api
  v
FastAPI prefork workers ---- Redis (rate limits, optional cache)
  |
  | SQL transaction
  v
PostgreSQL ---- mail_outbox ---- mail worker ---- SMTP
```

## Backend

`app/api` отвечает за HTTP и зависимости доступа. `app/services` содержит
бизнес-операции и повторно проверяет полномочия после получения row lock.
`app/db` задаёт схему, а Alembic хранит последовательность её изменений.
Сетевой слой ограничивает тело и время запроса, нормализует адрес клиента и
выставляет метрики.

HTTP-обработчик явно делает commit до формирования успешного ответа. Это важно:
финализатор FastAPI dependency выполняется слишком поздно, чтобы сообщить
клиенту об ошибке commit.

## Транзакции и конкуренция

Создание пользователя, организации, audit-записи и письма выполняется в одной
транзакции. SMTP не вызывается из HTTP-запроса. Worker арендует outbox-записи
через `FOR UPDATE SKIP LOCKED`, повторяет временные ошибки и помечает исчерпанные
попытки.

Изменение ролей сериализуется блокировкой строки организации. Deferred trigger
PostgreSQL проверяет конечное состояние транзакции: у каждой существующей
организации должен остаться активный владелец. Отдельный trigger не позволяет
отключить последнего активного суперпользователя.

## Процессы

`app.net.server` создаёт слушающий сокет с `SO_REUSEPORT`, запускает независимые
Uvicorn workers и перезапускает упавшие процессы с ограниченным backoff. SIGTERM
останавливает workers, SIGHUP выполняет последовательный restart. Prometheus
multiprocess-файлы умерших workers очищаются супервизором.

## Решения и ограничения

- PostgreSQL является источником истины. Redis можно отключить, но локальный
  rate limit тогда считается отдельно в каждом worker.
- Сессии серверные, поэтому отзыв применяется сразу, но каждый запрос читает БД.
- Tenant isolation реализована запросами и сервисами, а не PostgreSQL RLS.
  Добавление нового пути чтения требует отдельной проверки `org_id`.
- Миграции рассчитаны на PostgreSQL и не обещают совместимость с SQLite.

Причины решений зафиксированы в `docs/adr`.
