# Безопасность

Этот документ описывает защиту, которая есть в шаблоне, и то, что остаётся на
стороне команды эксплуатации. Он не заменяет аудит конкретного продукта.

## Границы модели

Шаблон рассчитан на браузерный клиент и недоверенную сеть. Он пытается
защититься от перебора паролей, кражи сессий, типовых межсайтовых атак,
спама, доступа между организациями и утечки данных из дампа БД.

Он не защищает от полного захвата хоста, физического доступа, компрометации
облачного аккаунта или уязвимостей в вашей бизнес-логике.

## Учётные записи

| Механизм | Реализация |
|---|---|
| Пароли | Argon2id, минимум 12 символов, простая проверка частых и похожих паролей. |
| Сессии | Непрозрачный случайный токен в cookie; в БД хранится только его SHA-256-хеш. |
| 2FA | TOTP. Секрет шифруется AES-256-GCM, шаг нельзя повторить, recovery-коды одноразовые. |
| Сброс пароля | Одноразовая ссылка с ограниченным сроком жизни. |
| Перебор | Счётчик по аккаунту и rate limit по IP и e-mail. |

Серверные сессии выбраны намеренно. Их можно сразу отозвать при смене пароля,
выходе со всех устройств или блокировке пользователя. JWT не нужен для этого
сценария.

Регистрация, вход и восстановление отвечают одинаково для существующего и
несуществующего e-mail. Это снижает риск перечисления пользователей.

## Запросы из браузера

- Session cookie имеет `HttpOnly`, `Secure` в HTTPS и `SameSite=Lax`.
- Изменяющие данные запросы проходят CSRF-проверку: Origin/Referer и
  подписанный токен, привязанный к текущей сессии.
- CORS не использует `*` вместе с cookie.
- API получает строгие security headers. CSP для JSON API запрещает ресурсы;
  страница клиента получает свою CSP от Caddy.
- Размер запроса, время обработки и keep-alive ограничены.

## Организации

- Доступ к данным организации проверяется в зависимостях API и в сервисах.
- Все запросы к участникам и отзывам ограничены `org_id`.
- Нельзя назначить роль выше собственной.
- В PostgreSQL есть отложенный trigger, не позволяющий оставить организацию
  без владельца. Row lock и транзакционный advisory lock закрывают гонки между
  параллельными изменениями владельцев и блокировкой пользователей.
- Инвайт адресный и одноразовый. Его может принять только пользователь с
  соответствующим e-mail.

## Публичные отзывы

Форма отзывов использует лимит по IP, скрытое honeypot-поле, защиту от повторов
и простую проверку ссылок. Ответ на спам выглядит как обычное подтверждение,
поэтому боту сложнее подбирать обход.

## Данные и логи

- Пароли, токены и recovery-коды не хранятся в открытом виде.
- IP сохраняется как HMAC, а не как исходный адрес.
- Существенные действия пишутся в аудит в той же транзакции, что и изменение.
- Логгер маскирует значения полей с секретами.
- Console-почта доступна только в development. В staging и production нужен
  SMTP, чтобы ссылки с токенами не попадали в журналы.
- Письма ставятся в outbox в той же транзакции, что и бизнес-изменение. Worker
  использует lease и повторные попытки, поэтому сбой SMTP не теряет событие.

Точные сроки хранения и процедура удаления описаны в
[политике данных](DATA_POLICY.md). Связь угроз, реализации и тестов приведена в
[матрице защитных мер](CONTROL_MATRIX.md).

## Что нужно сделать при эксплуатации

1. Хранить `.env` вне Git и с правами 0600.
2. Настроить HTTPS, SPF/DKIM/DMARC и SMTP.
3. Регулярно обновлять образы и зависимости.
4. Делать бэкапы и регулярно проверять восстановление.
5. Подключить `/metrics` к мониторингу и настроить алерты.
6. Периодически запускать сканирование зависимостей и аудит приложения.
