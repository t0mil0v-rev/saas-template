# Надёжность и восстановление

Числа ниже являются целями шаблона. Команда конкретного продукта должна
подтвердить их испытанием и изменить под договорные требования.

## Цели

| Показатель | Цель по умолчанию | Предпосылка |
|---|---:|---|
| RPO | до 24 часов | ежедневный успешный backup |
| RTO | до 2 часов | доступен проверенный backup и новый хост |
| Доступность API | 99.5% в месяц | один узел, без HA PostgreSQL |
| Доставка почты | 15 минут для временной ошибки | SMTP восстановился до исчерпания retry |

Один Compose-хост не обеспечивает высокую доступность. Отказ диска или хоста
прерывает сервис до восстановления. Для более строгой цели нужны внешний
PostgreSQL с репликацией, несколько API-узлов, общий Redis и балансировщик.

## Backup

`backup.sh` пишет дамп во временное имя, проверяет его через `pg_restore
--list`, атомарно переименовывает, при необходимости шифрует age и создаёт
SHA-256. Если recipient задан, но `age` отсутствует, операция завершается
ошибкой. Таймер systemd запускает backup ежедневно.

Храните минимум одну копию вне хоста. Приватный age key должен находиться в
другом контуре. Раз в квартал восстанавливайте последнюю копию на отдельной БД,
запускайте миграции и smoke tests, затем фиксируйте время и результат.

Совместимость текущих миграций и незашифрованного ephemeral backup проверяет
`make academic-drill` на отдельном Compose project. Фактическое время
восстановления сохраняется в `.academic-results/summary.json`. Квартальная
проверка внешней зашифрованной копии всё равно обязательна: она проверяет ещё и
хранилище, age key, пропускную способность и действия оператора.

## Восстановление

1. Остановить внешние изменения или включить maintenance page.
2. Проверить checksum и расшифровать копию.
3. Сделать страховочный backup текущей БД.
4. Остановить API и mail worker.
5. Запустить `restore.sh`, миграции и healthcheck.
6. Проверить вход, tenant isolation, очередь писем и последние audit events.
7. Зафиксировать фактические RPO/RTO и причину инцидента.

Restore намеренно fail-closed. После ошибки записи в БД остаются остановлены,
пока оператор не выяснит причину.

## Деградация

При недоступном Redis API продолжает работать с локальным limiter. Ограничение
становится отдельным для каждого worker, поэтому это аварийный режим, а не
эквивалент Redis. При недоступном SMTP бизнес-транзакции продолжаются, письма
остаются в outbox. Рост `failed_at` и возраста старейшей записи должен вызывать
alert.

## Миграции

Перед миграцией deploy делает backup. Alembic использует advisory lock, поэтому
две копии мигратора не меняют схему одновременно. Для необратимого изменения
данных нужен отдельный план rollback или forward-fix, проверенный на копии БД.
